# 陈晓卿美食足迹地图 PRD

> 文档状态：v0.6（前端结构澄清稿）
> 当前阶段：产品定义与范围收敛，不进入实现
> 已结合 `final_data_audit_v1`、封版实体/地点/到访/旅程数据修订。

## 1. 产品定义

### 1.1 一句话定位

一个基于陈晓卿公开微博记录构建的个人美食旅行知识库，让用户沿着时间与地图，探索他的美食足迹，并跟随这些真实记录发现一次次旅程。

产品对外叙事围绕四个关键词展开：

> 陈晓卿 · 美食地图 · 足迹 · 跟随

### 1.2 核心价值

本产品不是餐厅推荐榜，也不是普通 POI 地图。它呈现的是有时间、有来源、有上下文的“到访记录”：

> 2018 年春节，他在潮州的一次旅程中到访了这家店、吃了这些食物，并留下了这条微博记录。

每个可展示的地点都必须能追溯到至少一条公开记录。AI 是公开的数据整理方式，而不是事实来源；AI 生成或推断的地点匹配、菜品标签和旅程聚类，应与原始内容区分，并展示可信程度。

### 1.3 产品目标

用户可以：

1. 从旅程、时间、地区和主题入口浏览陈晓卿的美食足迹。
2. 打开一次旅程，按发生顺序查看地点、食物、微博正文和图片分析档案。
3. 查看一个城市或具体地点在不同年份的相关记录。
4. 按地区、时间、食物、菜系等条件检索已有记录。
5. 基于已收录的真实足迹，组合一条可浏览的主题路线。
6. 理解数据从原始微博到结构化结果的处理过程，并识别不确定信息。

### 1.4 非目标

当前阶段不承诺：

- 覆盖陈晓卿全部真实行程或用餐记录。
- 判断餐厅当前是否营业、品质是否仍然相同。
- 提供实时导航、订座、交通、价格或营业时间。
- 将路线包装成可以直接执行的完整旅游攻略。
- 允许用户发布点评、收藏、登录或同步个人数据。
- 让大语言模型直接编造查询结果或推荐产品库之外的地点。

### 1.5 发布与内容边界

- 产品最终面向公众发布。
- 站内可以展示原微博正文，并保留原微博链接。
- “查看 RAW”使用新页面打开原微博链接，避免用户离开当前探索状态。
- 原始图片不在站内展示，也不随公开站点数据分发。
- 图片仅作为离线分析输入；站内可展示 VLM 生成的描述、分类、候选菜品、可见食材、场景等结构化结果。
- 所有图片分析结果必须明确标注为“图片分析”，不能让用户误以为正在查看原图。
- 数据为一次性全量整理；发布后不计划持续增量更新，但仍需标注数据版本、覆盖时间和生成日期。

## 2. 用户与核心场景

### 2.1 目标用户

- 对陈晓卿、美食纪录片或地方饮食文化感兴趣的人。
- 想从真实内容中寻找旅行灵感的用户。
- 希望按地区、食材或菜系研究其长期美食轨迹的用户。

### 2.2 核心使用场景

#### 场景 A：随意探索

用户从首页理解人物、时间跨度和代表性旅程，通过年份、地区或主题入口进入感兴趣的内容。

#### 场景 B：复盘一次旅程

用户打开“2018 春节潮汕行”，沿时间顺序查看城市、餐馆、食物、微博正文和图片分析之间的关系。

#### 场景 C：查询特定记录

用户查找“2015 年以后在广东吃过的牛肉”，系统只返回满足条件且有来源的记录。

#### 场景 D：沿足迹规划主题路线

用户选择广东、5 天、粤菜，系统从已收录的到访记录中组合路线，并明确说明这是“基于历史足迹生成”，不是实时旅行建议。

## 3. 核心概念与关系

为避免“一个地点既代表城市又代表餐馆”的混乱，产品使用以下对象：

| 对象 | 定义 | 示例 |
|---|---|---|
| 原始记录（Post） | 一条公开微博及其发布时间、正文和媒体 | 2018-02-16 发布的微博 |
| 媒体（Media） | 微博内的图片或视频，以及分析结果 | 一张牛肉火锅图片 |
| 地理区域（Region） | 国家、省级、城市、区县等行政或文化地理范围 | 广东、潮州、顺德 |
| 具体地点（Place） | 可定位的餐馆、市场、摊位或景点 | 官塘兄弟牛肉火锅 |
| 到访事件（Visit） | 某个时间点或时间段对某一地点的访问，是内容关联的核心 | 2018-02-16 到访某店 |
| 食物实体（Food） | 菜品、食材、品类或菜系标签 | 牛肉丸、牛肉、火锅、潮州菜 |
| 旅程（Trip） | 在连续时间内，由一组到访事件和原始记录构成的行程 | 2018 春节潮汕行 |

### 3.1 必须成立的可追溯链路

```text
地图点 / 搜索结果
  → 到访事件
  → 具体地点或地理区域
  → 一条或多条原始记录
  → 原始媒体记录及其离线分析
  → AI 提取或匹配结果
```

规则：

- 具体地点没有来源记录时，不作为“陈晓卿去过”的事实展示。
- 同一家店多次出现时，复用地点实体，保留多次独立到访事件。
- 只知道城市、不知道具体餐馆时，允许创建城市级到访，但不得伪造具体 POI。
- 原文明确表达的信息与 AI 推断的信息必须能被区分。
- 低可信结果不得以确定语气呈现。

## 4. 信息架构

### 4.0 核心产品结构

前端收拢为三个核心模块：

```text
旅程浏览
├── 重点旅程
├── 时间线入口
└── 全部旅程独立页面

旅程详情
├── 旅程信息 + Geo-Graph
└── 当前选中节点的完整内容

自定义旅程复刻
├── P0：结构化条件生成
└── P1：LLM 自然语言输入
```

地点、地区、微博、图片分析和食物不是彼此平级的主模块，而是旅程及其节点的内容组成。旅程节点最终指向关联微博；地点、地区和微博需要独立查看时可以进入次级详情，但不占据一级导航。

### 4.1 主导航

```text
首页
├── 全部旅程
├── 复刻旅程
└── 关于数据
```

说明：

- 首页负责建立叙事、展示重点旅程和时间入口；全部旅程使用独立页面承载完整筛选与浏览。
- 地点、地区和 Post 详情作为次级页面或同页详情层存在，不进入一级导航。
- “复刻旅程”先使用结构化条件；后续 LLM 只作为另一种输入方式，不改变底层生成逻辑。

### 4.2 建议页面

| 页面 | 建议 URL | 主要任务 |
|---|---|---|
| 首页 | `/` | 建立叙事、展示重点旅程和时间入口 |
| 全部旅程 | `/trips` | 浏览并筛选全部封版旅程 |
| 旅程详情 | `/trips/{tripId}` | 复盘一次旅程 |
| 复刻旅程 | `/recreate` | 根据条件实时构建 `JourneyView` |
| Post/地点次级详情 | `/posts/{postId}`、`/places/{placeId}` | 查看完整来源或跨旅程关联 |
| 关于数据 | `/about-data` | 数据来源、方法、限制与版本 |

## 5. 功能需求

## 5.1 首页

### 页面目标

用户先理解“陈晓卿 × 美食 × 足迹”，浏览重点旅程，并通过时间或主题入口进入全部旅程页面。

### 必须展示

- 产品名称与一句话说明。
- 数据覆盖起止日期，而不是写死“16 年”。
- 核心数据指标：原始记录数、旅程数、到访事件数、具体地点数、覆盖城市数。
- 3–6 个重点旅程。
- 时间线或年份入口。
- “查看全部旅程”入口。
- 数据更新时间或版本。
- 克制但清晰的数据声明：内容由 AI 辅助整理与筛选，可能存在错误。

### 关键交互

- 点击年份或时间区间进入带有对应筛选条件的全部旅程页面。
- 点击重点旅程或旅程卡进入 Trip 详情。
- 用户可以随时进入全部旅程页面，不被重点策划内容限制。

### 规则

- 全部统计口径必须可解释。例如，“地点数”不得混合城市与餐馆。
- 时间轴默认展示全部年份；单年、连续年份区间的筛选方式待确认。
- 首页不承担复杂数据分析，首要任务是建立认知和引导进入内容。
- 数据覆盖尽量完整，但首页只使用稳定的规范字段做聚合；未归一化的长尾标签仍可在搜索和记录详情中出现。
- 由于 107 个封版 Trip 只覆盖 281 条 Post，不能把封版 Trip 描述为全部微博记录；未进入 Trip 的 Post 保留在全站搜索中，不强行归入旅程。

## 5.2 旅程 Geo-Graph

### 页面目标

只在具体 Trip 或用户生成的 `JourneyView` 中，用简洁的地理关系图表达“这次旅程按什么顺序经过了哪些地方”。

不提供全国或世界范围的独立可拖拽大地图，也不把地图作为首页首屏。参考 [Apache ECharts Geo Graph 示例](https://echarts.apache.org/examples/zh/editor.html?c=geo-graph) 的“淡化地理底图 + 节点 + 有向边”结构，但不原样照搬视觉样式。

### 适用范围

- 封版 Trip 详情。
- 用户查询后实时生成的 `JourneyView`。
- 不用于首页、地点列表、地区列表或全量 Post 总览。

### 图形结构

- 地理底图使用低对比度填充和细边界，只提供空间参照，不抢占视觉注意力。
- 默认自动聚焦到当前旅程的节点范围，不展示与旅程无关的大片区域。
- 行政区名称只保留与旅程相关或理解路线所必需的标签，避免示例中的全量地名干扰。
- 主路线节点显示顺序编号，不只使用无语义圆点。
- 主路线 `anchor`：实心节点。
- `candidate`：空心或半透明节点，并标注“可能地点”。
- `region_only`：区域环或范围型节点，不伪装成精确坐标。
- `context/revisit`：更小、更淡的上下文节点。
- 主路线使用有方向的实线；上下文关系使用弱化虚线或点线。
- 超过 500 km 的相邻边使用明显的过渡虚线，并标注为“时序连线，非导航路线”。

### 交互

- 点击节点选中对应 Visit，并联动时间线或内容卡。
- 点击时间线记录反向高亮图中节点和相关边。
- Tooltip 只展示地点名称、顺序、日期、代表食物和可信状态。
- 默认视图应完整容纳路线，不要求用户先拖动或缩放才能理解。
- 是否允许用户在 Trip 图内自由缩放和平移仍需确认；即使允许，也只是辅助探索，不是核心操作。
- 不使用持续飞线、呼吸闪烁等高干扰动画；方向箭头和轻量选中动效已经足够。

## 5.3 旅程列表

### 功能

- 按时间倒序或正序浏览。
- 按年份、地区、持续天数、食物主题筛选。
- 每项展示：标题、日期、持续天数、覆盖地区、到访数、原始记录数、代表性食物或场景描述。
- 旅程由算法聚类产生，展示聚类方法、数据依据和可信程度，不使用“人工确认”标签。

## 5.4 旅程详情

### 页面目标

以一次旅程为叙事单元，将时间、路径、地点、食物和原始内容串联起来。

### 页面骨架

页面由两个核心区域组成，桌面端可左右分栏，窄屏可上下排列：

1. **旅程区**：标题、时间、摘要、可信说明和 Geo-Graph。
2. **节点详情区**：以当前选中节点关联的微博为核心，显示其完整内容和分析结果。

进入页面时默认选中第一个主路线节点。点击 Geo-Graph 中的主点、候选点、区域点或上下文点后，节点详情区原地更新，不要求用户跳转页面。

### 必须展示

- 旅程标题、日期范围、覆盖地区、天数、到访数、原始记录数。
- 旅程 Geo-Graph 与按时间排序的路线。
- 旅程主题及其生成依据。
- 旅程聚类说明与可信程度。
- 当前节点的日期、地点、可信状态和关联关系。
- 当前节点关联的原微博正文与 RAW 链接；一个节点关联多条微博时按时间排列并允许切换。
- 图片分析摘要、图片角色和模型提取信息，不展示原图。
- 菜品、菜系、食材、品类、烹饪方式和餐馆/地点信息。
- 同一地点的其他到访或相关 Trip 入口。

### 关键交互

- Geo-Graph 节点与节点详情区双向联动。
- 点击节点查看其关联微博，以及地点、时间、相关食物和匹配说明。
- 点击原始记录进入站内正文详情，并可继续访问原微博链接。
- 允许查看原始顺序，不以 AI 文案替代原始内容。
- 主路线、候选点和上下文点默认同时可见；候选点与上下文点弱化显示，并提供“只看主线”开关。
- 点击节点只替换节点详情区的内容，保持旅程信息与图形上下文稳定。

### 异常情况

- 旅程中存在只有城市级位置的记录时仍保留在时间线，但不绘制伪精确路线。
- 时间只能精确到日期时，不虚构日内访问顺序。
- 跨日或顺序不确定时，明确标注“顺序未确认”。
- 超过 500 km 的相邻边保留为时序关系，但使用虚线或过渡线，并显示距离及“时序连线，非导航路线”说明。

## 5.5 次级地点与地区档案

地点与地区档案用于承接旅程节点、筛选结果和原始记录，不作为一级产品模块或主导航入口。

### 地区详情

展示：

- 地区名称、层级和上级地区。
- 到访次数、具体地点数、相关旅程数、原始记录数。
- 相关城市或下级地区。
- 代表食物与地点，并说明“代表”的计算口径。
- 按时间排列的相关旅程与到访。

### 具体地点详情

展示：

- 标准名称、原始文本名称、地点类型。
- 地址与坐标精度。
- 历次到访及相关旅程。
- 每次到访对应的微博、媒体与食物。
- 外部 POI 匹配来源、匹配状态和可信程度。

### 规则

- “出现次数”“到访次数”“微博数”分别统计，不混用。
- 餐厅更名、搬迁或同名分店不得默认合并。
- 营业状态未知时不展示“仍在营业”等暗示。
- 只有 Restaurant Entity、没有可用 Place 的餐厅不创建具体地点页，但仍可在搜索、原文高亮和记录详情中出现。
- 多候选餐厅使用“可能地点”表达，按现有匹配信息排序；摘要默认只显示排名第一的候选，展开后最多显示三个候选及局限说明。
- `source_geo` 地图点默认保留，但使用区别于已解析 POI 的视觉样式，并明确标注“来源定位，未逐点人工核验”。
- 餐饮 Place 进入地点列表，并在关联 Trip 的 Geo-Graph 中作为主要节点；酒店、景点、交通、学校等非餐饮 Place 只作为旅程上下文点，不与餐馆平级展示。

## 5.6 全部旅程

全部旅程使用独立页面承载。用户通过结构化条件逐步缩小 107 个封版 Trip，并可从任一结果进入复用统一结构的旅程详情页。

### 查询原则

- P0 只提供可输入、可选择的结构化条件；自然语言解析属于 P1。
- 结果必须来自结构化数据；无法满足时明确显示零结果。
- 系统不得为了“回答完整”而补充数据集之外的地点。
- 未进入封版 Trip 的 Post 不在此处强行关联；它们仍保留在全站搜索和原始记录详情中。

### 收录资格与地图资格

“是否具有美食档案价值”和“是否能够进入地图”是两个独立判断：

- **美食档案资格**：正文或图片存在可靠的美食、饮食文化或餐饮场景证据，不强制要求定位。
- **地图/轨迹资格**：存在可用的实际地点证据，例如原始 `geo`、正文中的地点/餐馆线索、图片中清晰可辨的招牌，或后续得到的可信 POI 匹配。
- IP 属地 `region_name` 不作为实际定位证据。
- 有实际定位但没有配图的原创微博进入文本 LLM 筛选，由正文判断是否具有美食记录价值。
- 图片被初筛为非美食，但正文或实际定位具有候选价值的原创微博，不直接删除，进入文本筛选。
- 正文明显记录食物但没有可靠地点的微博可以进入美食档案与查询结果，但不生成地图点或到访事件。

### 支持条件

- 地区：省级、城市、区县或文化区域。
- 时间：年份、日期范围、季节、春节等节日区间。
- 食物：具体菜品、食材、品类、菜系。
- 地点类型：餐馆、市场、摊位等。
- 旅程属性：持续天数、覆盖城市数、单城/跨城。
- 可信程度：是否包含低可信或存在歧义的结果。

食物 Facet 采用“固定维度 + 高频值 + 搜索全部”：

- 固定维度：菜品、菜系、食材、食物品类、烹饪方式。
- 每个维度的菜单优先展示高频规范标签。
- 搜索同时覆盖规范标签与未归一化长尾标签。

### 结果形态

- 记录列表：回答“有哪些”。
- 地点结果：回答“在哪里”；只有形成 Trip 或 `JourneyView` 时才生成 Geo-Graph。
- 时间结果：回答“什么时候”。
- 主题路线：回答“如何把这些足迹串起来”。

### 示例

输入：

> 2015 年以后，他在广东吃过哪些和牛肉有关的东西？

解析为可编辑条件：

```json
{
  "date_from": "2015-01-01",
  "region": "广东",
  "food_or_ingredient": "牛肉",
  "result_mode": "records"
}
```

## 5.7 自定义旅程复刻

### 定位

用户从全部历史足迹中选择条件，实时构建一个自己的 `JourneyView`。它是对已有记录的复刻与组合，不修改 107 个封版 Trip，也不是实时、最优或完整的旅行计划。

### 输入

- 必填：地区或主题至少一项。
- 可选：天数、食物/菜系、起点、结束点、是否接受跨城、最低可信程度。
- P0 使用表单、选项和关键词。
- P1 增加 LLM，将自然语言转换为同一套结构化条件；LLM 不直接生成事实地点。

### 输出

- 路线标题和生成依据。
- 按天或按站点排列的地点。
- 每个地点被选入的理由及对应来源记录。
- 地图线路。
- 未纳入但符合条件的候选地点。
- 限制说明，例如交通时间、营业状态和预约信息未验证。

生成结果直接复用 Trip 详情的双区域结构：一侧为旅程信息和 Geo-Graph，另一侧为当前节点关联微博。`JourneyView` 默认只在当前会话中临时存在，不写回或修改封版 Trip。

### 生成规则

- 只能选择存在至少一次有效到访的地点。
- 每个推荐点必须可展开到原始记录。
- 低可信地点默认不进入路线，除非用户主动允许。
- 若数据不足以覆盖用户指定天数，应减少天数或明确提示，不重复填充。
- 路线排序依据需要在产品中简要说明；具体规则待数据可用后确定。

## 5.8 原始记录详情

建议提供统一的记录查看层或独立页面，展示：

- 发布时间与原始链接。
- 原始正文。
- 图片数量与每张图片对应的 VLM 分析档案，不展示原图。
- 文本/图片分析提取出的地点和食物标签。
- 该记录参与形成的到访事件与旅程。
- AI 提取结果、处理版本和可信程度。

VLM 分析档案按原始图片顺序展示，但公开数据中不应包含可直接加载原图的 URL。页面需提示：“原图未在本站展示，以下内容为模型对原图的结构化分析。”

记录详情使用同一信息架构，根据实际字段自动改变模板：

- 有图片分析时展示逐图分析档案。
- 无配图时省略图片分析区，不留空白占位，并显示克制的“无配图”说明。
- 无配图不是降低记录价值或排序权重的充分理由；是否突出应由正文、地点、食物与旅程关联决定。
- RAW 记录显示完整微博发布时间；Visit 和 Trip 时间线默认只显示日期，并统一提示“到访时间以微博发布时间近似”。

## 5.9 关于数据

### 必须说明

- 数据来源与收集范围。
- 数据覆盖起止时间、记录数和数据生成日期。
- 数据处理流程。
- 哪些字段来自原文，哪些来自图片分析，哪些来自外部 POI，哪些为算法推断。
- 可信程度的含义和分档规则。
- 当前没有逐条人工校验这一限制。
- 已知缺失、错误与偏差。
- 内容纠错或反馈方式（若项目计划提供）。

AI 提醒分为两层：

1. 全站说明：“本站内容由 AI 辅助整理与筛选，可能存在遗漏或错误。”
2. 字段级来源：“原文提及 / 图片分析 / POI 匹配 / 系统推定”。

### 建议处理流程表述

```text
公开微博
→ 原始字段整理
→ 图片美食相关性初筛
→ 美食图片深度分析
→ 文本与图片实体/标签归一化
→ 地区与 POI 匹配
→ 到访事件构建
→ 旅程聚类
→ 质量规则检查
→ 冻结并发布站点数据版本
```

## 6. 可信度与来源表达

不要只展示一个无法解释的“92%”。每类推断应有独立状态：

| 推断类型 | 建议状态 |
|---|---|
| 地点识别 | 原文明确 / 外部地理信息补全 / 模型推断 / 未知 |
| POI 匹配 | 唯一高可信候选 / 多候选 / 低可信 / 未匹配 |
| 食物识别 | 原文提及 / 图片可见 / 文图综合推测 |
| 旅程归属 | 规则聚类 / 边界不稳定 / 无法归入 |
| 时间顺序 | 精确时间 / 仅日期 / 推定顺序 / 未知 |

由于不计划逐条人工校验，产品不能使用“已确认”“真实菜名”等暗示人工背书的状态。面向普通用户优先显示易懂状态；原始分数与证据来源可在“数据详情”中展示。阈值和分档规则必须随数据版本固定，不能在不同页面使用不同解释。

## 7. 数据交付期望

数据由其他流程先行处理。本节不规定实现方式，只定义现有结果如何进入产品，以及下一阶段应避免遗漏的字段。

### 7.1 数据分层

数据不能直接从 VLM 输出跳到产品展示，应保留三个层级：

1. **原始记录层**：微博原始字段、图片顺序和原始链接，尽量保持不可变。
2. **分析结果层**：初筛、细筛、文本提取、POI 搜索和聚类的原始输出，保留各自版本。
3. **产品实体层**：把多个分析结果归一化为 Post、Media、Food、Region、Place、Visit 和 Trip，供筛选、地图和页面使用。

同一个分析候选即使置信度较高，也不能自动等同于最终实体。例如，VLM 输出“潮菜”只是一个候选标签，需在产品层归入“菜系/地域风格”，不能与“海鲜”这一食物品类混在同一维度。

### 7.2 已有原始微博字段

当前数据已经包含：

```text

mid
type
author
author_uid
created_at
url
title
content
reposts
comments
likes
pics[]
article_url
retweet_of
geo

```

使用规则：

- `id` 或 `mid` 可作为 Post 的稳定来源 ID。
- `created_at` 是微博发布时间，不必然等于拍摄时间或实际到访时间。
- `geo` 可作为地理证据，但仍需记录其原始结构与精度。
- `region_name` 是 IP 属地，不应作为实际到访地点或 POI 匹配依据。
- `pics[]` 仅用于离线处理；发布到公开站点的数据应移除原图 URL。
- 转发、评论和点赞是抓取时的快照数据，当前不作为核心产品指标。
- 产品数据只收录原创微博；`retweet_of` 非空的记录在进入分析流水线前排除，并统计排除数量。
- `article_url` 需要保留，以免原创长文的来源链断裂。

### 7.5 VLM 阶段 B 细筛字段

阶段 B 只负责细化上一级认为有分析价值的图片。字段覆盖图片摘要、角色、候选菜品、食物类别、可见食材、烹饪方式、菜系、餐馆场景、场景特征、记录背景和档案价值。

#### A. 对齐图片角色枚举

初筛包含 `food_material` 和 `person_with_food`，细筛的 `image_role` 当前没有完全对应。建议至少使用：

```text
dish
food_material
restaurant
menu
person_with_food
food_scene
non_food
unknown
```

否则“干货食材”等图片会被迫错误归入 `dish` 或 `food_scene`。

#### B. 为关键候选项保留来源

为控制 7,573 张图片的输出规模，不要求每个字段都生成证据文本。`dish_candidates`、`food_categories`、`cooking_methods`、`cuisine_style` 以及地点候选保留：

```text
name 或 type
confidence
source: text | image | combined
```

`ingredients_visible` 的来源固定为当前图片，因此只保留名称和置信度。

#### C. 不把不同标签层级混用

- `dish_candidates`：具体菜品，如“韭菜辣椒炒干河虾”。
- `food_categories`：食物品类，如“海鲜”“面食”“汤”“点心”。
- `ingredients_visible`：可见食材，如“干河虾”“韭菜”。
- `cooking_methods`：烹饪方式，如“炒”“炖”。
- `cuisine_style`：菜系或地域风格，如“潮菜”“徽菜”。

示例中的“潮菜”应只进入 `cuisine_style`，不应同时出现在 `food_categories`。

#### D. 增加可核查的文字与地理线索

为后续高德 POI 搜索和地点消歧，建议细筛增加：

```text
visible_text[]        图片中清晰可辨的招牌、菜单或包装文字
place_clues[]         图片或正文中的地点线索，不等同于最终地点
restaurant_name_candidates[]
```

候选地点至少包含 `name`、`confidence`、`source`；无法确认时返回空数组。候选只作为后续 POI 搜索输入，VLM 不直接生成坐标或标准 POI。

如果另有专门 OCR 或正文实体抽取流程，这三类字段也可由相应流程提供，但最终分析层必须能保留原始证据。

#### E. 由运行流程记录分析版本与处理状态

每张图的细筛结果建议额外保留：

```text
media_id
pic_index
analysis_version
model
prompt_version
processed_at
status
error
```

`media_id` 应由 `post_id + pic_index` 稳定生成或映射，避免图片 URL 变化后失去关联。`status` 至少区分成功、跳过和失败。

#### F. 明确 `importance` 的含义

保留现有 `importance: high | medium | low` 字段，但在提示词中明确：它只表达图片对美食档案、地点识别或旅程叙事的资料价值，不是品质评价。

#### G. 区分简短摘要与补充说明

- `summary`：100 字以内、可公开展示的客观描述。
- `notes`：分析限制、证据冲突和不确定项，主要用于数据解释。

`notes` 不应重复全部标签，也不应用来存放只有程序才能解析的关键字段。

### 食物信息的“全量保留、分层呈现”

P0 不丢弃阶段 B 中的菜品、食材、品类、烹饪方式和菜系信息，也不为追求整齐而再次调用 LLM 补全。使用三层结构：

1. **原始分析标签**：保留名称、置信度和来源，可用于记录详情与全文搜索。
2. **规范 Facet**：通过确定性别名表和受控词表生成，用于筛选、聚合和统计。
3. **未归一化长尾**：没有可靠映射时保持原样，`facet_id` 为空；仍可搜索和查看，但不进入聚合菜单。

建议优先建立：

- 菜系别名：如“潮菜 / 潮汕菜”“安徽菜 / 徽菜”。
- 烹饪方式别名：如“炸 / 油炸”“炖 / 炖煮”。
- 食物品类别名：如“肉类 / 肉类菜肴”等需要产品口径判断的近义项。
- 高频食材别名：只处理高频、明显同义的写法，不强制覆盖全部 6,507 种写法。
- 菜品 Entity 继续使用现有规范结果，原始图片候选作为补充搜索文本。

规范过程不得覆盖原始值。每条映射至少保存：

```text
raw_label
facet_id
facet_name
facet_type
mapping_method
mapping_version
```

`food_related` 与 `importance` 只用于内部排序、质量检查或默认内容密度控制，不作为面向用户的筛选条件。

食物标签不设置硬删除线，按可信程度分层呈现：

- 高可信：正常展示。
- 中可信：使用“可能”语气。
- 低可信：收纳在“更多模型推测”中，仍保留在数据详情，并允许精确搜索命中。

具体分档阈值应根据不同字段的实际置信度分布确定，不能假定所有模型字段使用同一阈值。

### 7.13 Trip（旅程）

```text
id
title
title_source
start_date
end_date
date_precision
visit_ids[]
post_ids[]
region_ids[]
theme_food_ids[]
summary
cluster_method
cluster_params
confidence
quality_flags[]
```

封版已经重新生成 781 个 Visit 和 107 个 Trip。Trip 使用 `st_dbscan_graph_v1 + home_boundary_split_v1`，主要参数为：

```text
near_km: 100
near_days: 5
travel_km: 2500
travel_days: 2
min_samples: 2
```

107 个 Trip 中包括 53 个本地连续记录、49 个目的地停留和 5 个跨城路线。主路线只包含 285 个 Visit、281 条 Post；这是保守门槛的策展视图，不能替代全部 3,236 条 Post 的搜索和时间线。

Trip 成员关系已经冻结，LLM 只生成标题、副标题、摘要和亮点，没有改变路线成员。产品文案使用“系统整理的旅程”，不把聚类边界或微博发布时间描述为作者真实定义的旅行与实际到店时间。

### 7.14 数据质量检查

交付前建议检查：

- 每个已发布到访是否至少有一条来源记录。
- 每个具体地点是否至少关联一次到访。
- 引用的 Post、Media、Place、Visit、Trip ID 是否存在。
- 时间范围是否自洽，旅程开始时间不晚于结束时间。
- 坐标是否落在声明的地区内，或明确标记异常。
- 同名分店、迁址和重复 POI 是否保留待确认状态。
- 食物标签是否有明确层级与来源。
- 初筛与细筛结果是否能通过 `post_id + pic_index` 稳定关联。
- 公开站点数据是否已经移除原图 URL。
- 所有 `retweet_of` 非空的记录是否已从产品数据排除并计数。
- 进入地图的记录是否具有独立于 IP 属地的地点证据。
- 没有地点证据的美食记录是否仅进入档案、没有生成地图点。
- 文本提及、图片可见和文图综合推测是否被分别保留。
- 汇总指标能否从明细数据重新计算。

### 7.15 封版后的数据处理决策

| 处理项 | 是否单独处理 | 是否需要 LLM | 结论 |
|---|---|---|---|
| 公开字段白名单与 JSON 拆分 | 是，但属于建站数据构建 | 否 | 必须执行；移除原图 URL、模型响应、Token 和内部字段 |
| Post/Entity/Place/Visit/Trip 关联组装 | 否 | 否 | 现有 ID 足够，按页面需求确定性组装 |
| 原文 mention 高亮 | 否 | 否 | 已有字符范围和 Entity ID，直接使用 |
| Trip Geo-Graph 生成 | 否 | 否 | 使用 Visit、route 和 map role 确定性生成 |
| Place 类型归一化 | 是 | 否 | 必须新增一个小型映射层 |
| Region 展示名与行政层级 | 是 | 否 | 根据省、市、区县字段生成 |
| 菜品/菜系搜索 | 否 | 否 | 最终 Entity 已支持 |
| 食材/品类/烹饪方式筛选 | 是 | 否 | 使用规则、别名和受控词表；映射失败的原始标签仍可搜索和查看 |
| 13 个阶段一异常媒体 | 已完成 | 已定向处理 | `stage1_missing_13_merge_v1` 已合入，阶段一缺失为 0 |
| 8 条实体 LLM 无效结果 | 否 | 否 | 已有确定性 mention，不构成阻断 |
| 43 条到访 LLM 无效结果 | 暂不 | 暂不 | 全部已降级为搜索记录；网页验证出现明显缺口后再定向处理 |
| 餐厅未匹配或多候选 | 保留现状 | 否 | 606 个未匹配、80 个多候选；不应为了提高数量强行选 POI |
| Trip 叙事 | 否 | 否 | 107 个已有完整叙事，不再生成 |

Facet 归一化遵循“映射成功才聚合，映射失败仍保留”的原则，因此既不会截断信息，也不会产生额外 LLM 补全成本。

微博的转发数、评论数和点赞数作为抓取时历史快照保留在内部 Post。P0 不使用这些指标排序，也不要求在普通页面展示；后续如展示，只能标注为“抓取时数据”，不能暗示实时热度。

## 8. 视觉与内容原则

视觉基线参考 `docs/DESIGN-elevenlabs.md`，但需要为中文内容和地图产品做适配。

### 原则

- 采用杂志式、克制、留白充足的叙事感，而不是工具后台风格。
- 暖白底、近黑正文，柔和渐变只作氛围，不承担数据编码。
- 地图、路线、可信状态等功能信息必须有稳定且可访问的数据色彩体系，不能只依赖氛围渐变。
- 大标题中文字体需另行选择；Waldenburg 不适用于中文正文。
- 原始微博内容与 AI 总结在排版上明确区分。
- 在不展示原图的情况下，用“微博原文 + 图片分析摘要 + 标签证据”形成内容卡；不得生成仿真图片替代原图。
- Geo-Graph 与时间线在移动端不能简单压缩桌面双栏，需要定义主次顺序。

### 内容语气

- 用“记录显示”“数据中可见”“系统推定”，避免把不完整数据说成完整事实。
- 用“曾记录到访”而不是“推荐”。
- 用“基于历史足迹生成”而不是“最佳路线”。
- 不把 AI 可信度包装成权威结论。

## 9. MVP 范围建议

### P0：首个可用版本

- 首页：项目叙事、重点旅程和时间入口。
- 全部旅程独立页面及结构化筛选。
- 旅程详情：旅程信息、旅程 Geo-Graph、当前节点完整内容。
- 自定义旅程复刻：通过结构化条件生成临时 `JourneyView`。
- 次级原始微博、地点与地区详情页。
- 菜品、菜系、食材、食物品类和烹饪方式的分层搜索；聚合筛选只显示已进入规范 Facet 的值。
- 原始记录查看与 RAW 外链。
- 全站级 AI 数据说明和字段级来源、可信状态提示。
- 桌面端和移动端的基本可用性。

### P1：数据稳定后

- 在自定义旅程复刻模块中加入 LLM 自然语言输入，并展示可编辑的解析条件。
- 更丰富的策划型专题入口。
- 纠错反馈。

### 暂不进入范围

- 登录、收藏、分享清单。
- 实时路线优化和导航。
- 餐厅营业状态、价格、预约。
- 个性化推荐。

P0 的复刻入口支持手动输入关键词与选择筛选项，并将结果组织为临时 `JourneyView`。P1 再由 LLM 把自然语言转换为同一套可编辑条件，不另建一套生成逻辑。

## 10. 成功标准

在没有实际流量基线前，首版先使用可验证的产品标准：

- 用户能在首页快速说清该站点是“有来源的个人美食足迹”，而不是通用餐厅地图。
- 任一旅程节点、地点页或路线站点都可追溯到原始记录。
- 用户能在不依赖自然语言输入的情况下完成一次地区或食物查询。
- 不确定的地点、食物或旅程不会以确定事实展示。
- 汇总数字与明细数据一致。
- 主要浏览链路在移动端可完成。

上线后再补充行为指标，例如进入旅程详情率、旅程节点展开率、有效查询率、原始记录查看率和零结果率。

## 11. 已确认决策与剩余问题

### 已确认

- 网站公开发布，项目名称和主叙事直接包含陈晓卿。
- 正式名称暂定为“陈晓卿美食足迹地图”。
- 首屏关键词为“陈晓卿、美食地图、足迹、跟随”。
- 展示微博正文和原微博链接，不展示原图；可以展示图片的 VLM 分析结果。
- 原微博链接通过新页面打开，作为“查看 RAW”入口。
- 产品只收录原创微博，转发微博在分析前排除。
- 美食档案资格与地图资格分开判断；定位不是进入美食档案的硬性前提。
- 有实际定位但没有美食图片的原创微博进入文本 LLM 补筛。
- 数据来自一次性全量抓取与处理，后续不做增量更新。
- 暂不安排大规模人工校验，不能使用暗示人工确认的产品状态。
- P0 使用手动输入和结构化筛选，自然语言查询不是首版必需。
- 旅程已在 VLM、文本实体、到访判断和高德 POI 数据完成后重新生成并封版。
- 107 个 Trip 成员关系永久封版；后续不因页面查询或数据展示调整而改变。
- 用户查询生成的路线属于运行时 `JourneyView`，与封版 Trip 相互独立，不回写历史旅程。
- 无图 Post 根据字段自动使用简化模板，并显式说明“无配图”，但不因无图自动降低数据价值。
- 未匹配餐厅不创建 Place 页面，但保留搜索、原文高亮和记录详情入口。
- 多候选地点与 `source_geo` 点默认保留，通过“可能”“来源定位”等文案和视觉状态表达不确定性。
- `food_related` 与 `importance` 只用于内部处理，不作为用户筛选条件。
- 非餐饮 Place 只作为 Trip 上下文点，地点列表以餐饮地点为核心。
- 动态 `JourneyView` 默认只使用高可信 Place；用户可以主动开启“包含全部可能数据”，纳入 `source_geo`、多候选和其他低可信地点。
- 微博互动数仅作为历史快照保留，P0 不参与排序，默认不展示。
- 74 个 `region_only` 到访默认进入地图，但以区域点而非精确 POI 表达。
- Trip 候选点和上下文点默认弱化显示，并提供“只看主线”开关。
- RAW 页面显示完整发布时间；Visit 与 Trip 使用日期并声明时间代理。
- 超过 500 km 的相邻边使用虚线或过渡线保留时序关系，不表达导航路线。
- 不建设首页大地图或独立全量地图；Geo-Graph 只服务具体 Trip 和动态 `JourneyView`。
- 产品主体收束为旅程浏览、旅程详情和自定义旅程复刻三个模块。
- 首页先建立“陈晓卿 × 美食 × 足迹”的编辑式叙事，提供重点旅程和时间入口；全部旅程使用独立页面承载完整筛选。
- 旅程详情采用两个联动区域：旅程信息与 Geo-Graph，以及当前选中节点的完整内容；桌面端可左右分栏，窄屏上下排列。
- 旅程节点以关联微博为内容落点；一节点关联多条微博时可在详情区切换。
- 能依据现有关系关联到 Trip 的候选记录或上下文记录可以弱化、半透明展示；没有可靠关系的 Post 不强行绑定，只保留在搜索中。
- 自定义旅程复刻在 P0 使用结构化条件，结果复用旅程详情页面并临时存在；P1 在同一模块增加 LLM 自然语言入口。
- 首页明确说明数据由 AI 辅助整理与筛选，结果可能有误；具体页面继续展示来源和不确定性。

### 开工判断

当前产品结构已经足够进入首版设计与实现。剩余的响应式布局比例、Geo-Graph 辅助缩放和卡片密度属于实施阶段可验证的交互细节，不再作为开工前置问题。

## 12. 当前技术约束（待产品确认后另立技术文档）

已知方向是静态 Web、前端读取结构化数据。具体框架、地图引擎、LLM 服务、文件拆分与调用方式不属于本 PRD 的产品需求，后续应在数据规模和功能范围确认后写入技术设计文档。

自然语言解析如使用 LLM，其职责仅限于把用户输入转换为受约束的查询条件；模型名称、价格和示例代码不写入 PRD，以免产品定义与易变实现细节耦合。
